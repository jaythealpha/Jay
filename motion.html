카메라 AR 미리보기

휴대폰 카메라로 실제 QR(인쇄물이나 다른 화면)을 비추면, 이 페이지가 매 프레임 QR의 네 모서리를 찾아 그 위에 모션을 원근 변환해 덧씌웁니다. 기본 카메라 앱은 이렇게 할 수 없고, 반드시 웹페이지를 먼저 열어야 합니다.

실현 가능성 검토

헤드리스 Chromium에서 각 스타일의 한 루프를 프레임 단위로 캡처해 jsQR로 직접 디코딩한 결과입니다.

기본 설정(형성 2.4초 · 유지 2.2초 · 해체 1.2초, 루프 6.15초, 30fps = 184프레임), 내용 https://jay-inky.vercel.app (버전 4, 오류정정 H). 사각·원형 점 모두 같은 결과.

a) 움직이는 QR도 스캔되나요?

  • 완성된 프레임만 확실히 스캔됩니다. 측정한 모든 스타일에서 ‘완성’ 표시가 켜진 프레임은 100% 디코딩되었고, 잘못 읽힌 프레임은 0개였습니다.
  • 오류정정 H(약 30% 복원) 덕분에 거의 완성된 직전·직후 프레임도 일부 읽혀, 실제 디코딩 비율(43–58%)이 이론상 완성 구간(36–41%)보다 높습니다. 다만 이 덤에 기대지 말고 유지 구간을 1.5초 이상(권장 2초 이상) 두세요. 휴대폰 카메라는 초점·노출을 잡고 인식하는 데 보통 0.5–1.5초가 걸립니다.
  • 호흡 스타일은 점이 최대 16%만 줄었다 커지므로 루프 전체(100%)가 스캔됩니다. 포스터·사이니지처럼 ‘언제 비춰도 읽혀야 하는’ 곳에 적합합니다.
  • 발견한 함정: 원형 점 모드에서 정렬 패턴(오른쪽 아래 작은 사각)을 낱개 원으로 그리면 jsQR 인식률이 0%로 떨어졌습니다. 그래서 파인더·정렬 패턴은 항상 한 덩어리로 또렷하게, 가장 먼저 내려앉도록 그립니다.

b) 영상으로 쓸 수 있나요?

  • WebM(VP9/VP8): canvas.captureStream() + MediaRecorder로 데스크톱 Chrome·Edge·Firefox, Android Chrome에서 바로 녹화됩니다(30fps, 8Mbps, 루프 1회). 실시간 녹화라 탭을 앞에 두어야 하며, Chrome WebM에는 길이 메타데이터가 없어 일부 편집기에서 길이가 비어 보일 수 있습니다.
  • Safari(macOS·iOS 14.5+): MediaRecorder는 있지만 WebM 대신 MP4(H.264)로 녹화되며, 이 페이지는 자동으로 MP4로 저장합니다. 지원하지 않는 브라우저에선 안내 문구를 띄웁니다.
  • MP4가 꼭 필요하면: WebCodecs VideoEncoder(H.264) + mp4-muxer로 프레임 단위 오프라인 인코딩이 가장 깔끔합니다(실시간 제약 없음, 정확한 30fps, 인스타·카톡 호환). Chrome·Edge·Safari 16.4+ 지원, Firefox는 130+부터.
  • GIF: 어디서나 재생되지만 256색·용량 큼(수 MB)·부드러움 저하. 흑백 QR은 색 문제는 없으나 2–3배 큽니다. 웹엔 WebM/MP4, 메신저 스티커 용도만 GIF를 권장합니다. 어떤 형식이든 영상 속 QR은 유지 구간에서만 스캔된다는 점은 같습니다.

c) “카메라로 QR을 비추면 모션이 나타나는” AR

  • 기본 카메라 앱만으로는 불가능합니다. iOS·Android 카메라는 QR에서 URL만 읽어 링크를 띄울 뿐, 그 위에 그래픽을 그릴 수 없습니다.
  • 그래서 순서는 ① QR 스캔 → ② 웹페이지 열림 → ③ 페이지가 getUserMedia로 카메라를 켜고 → ④ 매 프레임 jsQR로 QR의 네 모서리를 찾아 → ⑤ 그 사각형에 원근 변환(호모그래피, CSS matrix3d)으로 모션을 덧씌웁니다. 위의 ‘카메라 AR 미리보기’가 정확히 이 방식이며, 헤드리스 테스트에서 가짜 카메라 영상 위 QR을 추적해 오버레이가 붙는 것을 확인했습니다.
  • iOS Safari·Android Chrome 모두 HTTPS에서 동작합니다(이 사이트는 Vercel HTTPS라 OK). 640px로 줄여 디코딩하면 최신 폰에서 대략 15–30fps가 나오지만, 모서리 추정이 프레임마다 흔들려(지터) 스무딩이 필요하고, 빠르게 움직이거나 QR이 작거나 반사가 있으면 추적이 끊깁니다. 또 오버레이가 QR을 가려도 인식은 원본 카메라 영상에서 하므로 문제없습니다.
  • WebXR 이미지 트래킹은 Chrome 실험 플래그 수준이며 iOS Safari엔 없어 아직 쓸 수 없습니다. 더 안정적인 추적이 필요하면 MindAR 같은 이미지 트래킹 라이브러리(별도 마커 학습 필요)나 8th Wall류 유료 SDK가 대안입니다.

a) Does a motion QR scan?

  • Fully-formed frames scan reliably. In every style, 100% of frames flagged “fully formed” decoded, with zero mis-reads.
  • Thanks to error-correction level H (~30% recovery), nearly-formed frames just before/after the hold also decode, so measured decode rates (43–58%) exceed the analytic formed window (36–41%). Don't rely on that bonus — keep the hold ≥ 1.5 s (2 s+ recommended). Phone cameras typically need 0.5–1.5 s to focus, expose and lock.
  • Breathe only shrinks modules by up to 16%, so the whole loop (100%) scans — good for posters and signage that must read at any moment.
  • A pitfall we found: in round-dot mode, drawing the alignment pattern (the small square near the bottom-right) as loose circles dropped jsQR decoding to 0%. Finder and alignment patterns are therefore always drawn as crisp single units that land first.

b) Can it be used as a video?

  • WebM (VP9/VP8): canvas.captureStream() + MediaRecorder records directly in desktop Chrome, Edge, Firefox and Android Chrome (30 fps, 8 Mbps, one loop). It records in real time, so the tab must stay in front; Chrome's WebM has no duration header, so some editors show an empty length.
  • Safari (macOS, iOS 14.5+): MediaRecorder exists but records MP4 (H.264), not WebM — this page falls back to MP4 automatically, and shows a message where recording isn't supported at all.
  • If you need MP4 everywhere: WebCodecs VideoEncoder (H.264) + mp4-muxer encodes frame by frame offline — no real-time limit, exact 30 fps, plays in Instagram/KakaoTalk. Chrome, Edge, Safari 16.4+; Firefox 130+.
  • GIF plays everywhere but is 256 colours, heavy (several MB) and less smooth; a black-and-white QR has no palette issues but files are 2–3× larger. Use WebM/MP4 for the web and GIF only for chat stickers. In any format, the code in the video only scans during the hold.

c) “Point the camera at the QR and the motion appears” (AR)

  • Not possible with the native camera app. The iOS/Android camera only reads the URL from a QR and offers a link; it can't render anything on top.
  • The flow must be: ① scan → ② a web page opens → ③ it starts the camera with getUserMedia → ④ every frame, jsQR returns the code's four corners → ⑤ the motion is drawn onto that quad with a perspective warp (homography via CSS matrix3d). The “Camera AR preview” above does exactly this; in headless testing it tracked a QR in a fake camera feed and attached the overlay.
  • Works in iOS Safari and Android Chrome over HTTPS (this Vercel site qualifies). Decoding at 640 px gives roughly 15–30 fps on recent phones, but the corner estimate jitters frame-to-frame (needs smoothing), and tracking drops with fast motion, small codes or glare. Covering the code with the overlay is fine because detection runs on the raw camera frame.
  • WebXR image tracking is still behind a Chrome flag and absent from iOS Safari, so it isn't usable yet. For sturdier tracking, use an image-tracking library such as MindAR (needs a trained marker) or a commercial SDK like 8th Wall.
