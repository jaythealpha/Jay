# Decision Log

POC를 만들면서 내린 기술적 결정과 그 이유.

## D1. 메인 트랙으로 Animated Drawings 채택

**결정**: 트랙 A(Meta Animated Drawings)를 메인, 트랙 B(생성형 API)를 비교군으로.

**이유**:
- 앱의 핵심은 "캐릭터가 *우리 집*에 *계속* 산다"는 일관성. 매번 다른 모션이 나오는 생성형은 그 일관성을 깬다.
- 비용 구조: 자체 호스팅이 사용자당 한계 비용을 0에 가깝게 만듦. 구독 모델과 궁합이 좋음.
- 결과가 BVH(뼈대 모션 데이터)이므로 향후 "집 안에서 캐릭터끼리 인터랙션" 같은 게임 엔진 연계가 쉬움.

**대안**:
- Kling/Veo만 사용 → 퀄리티는 좋지만 위 일관성·비용 문제.
- 두 트랙 동시 사용 → MVP에서 결정. 첫 깨어남은 생성형, 일상 모션은 리깅.

## D2. Docker 기반 셋업

**결정**: Animated Drawings는 Docker Compose로 격리.

**이유**:
- Python 3.8 + 무거운 ML deps(Detectron2, TorchServe)가 시스템 Python을 오염시킴.
- 사용자 환경 차이를 흡수.
- 향후 클라우드 배포 시 동일 이미지 재사용 가능.

**대안**:
- conda env → 호환성 문제 잦음. 기각.
- 서버리스(Modal/Replicate) → MVP 단계에선 좋지만 POC는 로컬 검증이 우선.

## D3. CLI 우선, UI 없음

**결정**: POC 단계에선 CLI만. 웹 데모는 다음 단계.

**이유**:
- POC의 목적은 "기술이 되는가" 검증이지 "쓰기 편한가" 검증이 아님.
- UI를 만들면 빌드 시간이 4배쯤 늘고 본질이 가려짐.

## D4. CPU 우선, GPU는 옵션

**결정**: 기본 도커 이미지를 CPU 베이스로.

**이유**:
- 개발자 노트북에서 검증할 수 있어야 빨리 반복함.
- 처리 시간은 1분 수준이면 비동기 UX("그림이 깨어나는 중...")로 충분히 흡수 가능.
- 프로덕션은 어차피 클라우드 GPU(L4/T4)로 갈 것이므로 POC에서 GPU에 시간 쓰는 건 낭비.

## D5. 모델 가중치는 빌드타임에 다운로드

**결정**: Dockerfile 안에서 `download_models.sh`로 가중치 패키징.

**이유**:
- 첫 실행 지연 제거.
- 재현 가능성 확보 (네트워크 끊겨도 컨테이너는 동작).

**리스크**: 이미지 크기가 커짐(~3~5GB 예상). 캐시 레이어로 완화.

## 미결정 / 추후 결정

- **U1**: Track A의 Python 3.8 EOL. 업스트림이 따라오지 않으면 우리가 fork해서 3.11로 업그레이드할지.
- **U2**: 모델 추론을 클라우드로 옮길 때 Modal vs Replicate vs 자체 GPU 인스턴스. POC 결과 본 뒤 결정.
- **U3**: 비-사람 그림(동물, 사물)을 트랙 B로 라우팅할 분류기. v2 POC에서 검증.
